AgentCore Gateway — Unified Inference Governance Plane

How it works, in depth. One governed front door for serverless inference, enforced identically across bedrock-mantle and bedrock-runtime. Every element below is deployed by CDK and verified against live infrastructure.
Start at README.md for what this is and how to deploy it; see docs/FINDINGS.md for why each mechanism was chosen over the obvious alternative.

Layers 1–4 execute in that order, so the first layer to object is the status the caller sees. There used to be a fifth — a native token rate limit between layers 2 and 3 — and deleting it is the point: it attached only on recognised inference paths, so it never metered the runtime passthrough. With it gone the interceptor is the only layer that can return a 429, which makes verdicts identical on both surfaces by construction rather than by ordering luck. Note that both upstream hops are SigV4-signed with the same gateway execution role — the caller never holds AWS credentials either way. The two differ only in target type and therefore in how the SigV4 service name is set. Detail for every element follows.

Layer 2 is fail closed. If it cannot establish policy — a config read fails, a counter write fails, ApplyGuardrail errors, or it runs short of invocation budget — it returns 403 rather than forwarding the request. Two mechanisms hold that invariant:

1. A self-imposed deadline. Before each control the interceptor checks context.get_remaining_time_in_millis() against that control's estimated cost plus a safety margin, and denies with 403 governance_timeout if there is not enough left. The Lambda timeout (20s) is headroom, not a deadline — sized so the internal check always fires first, because the function must never be killed mid-flight.

2. A thin wrapper. handler() does nothing but call the governance body and convert anything it raises into a typed 403. A control added later therefore cannot introduce a fail-open path by forgetting to handle something.

Denials distinguish "you are not allowed" from "we could not establish whether you are allowed". model_access_denied is a user meeting policy; governance_unavailable and governance_timeout are operational failures and should be alarmed on separately.

Why this is not the gateway default: an interceptor that times out makes the gateway return 200 with the model invoked and no governance applied. That is measured, undocumented, and not configurable — see docs/FINDINGS.md.
Layer 2 is also retry-safe and recoverable. The AgentCore devguide states the gateway "may retry requests to interceptor Lambda functions in case of failures or timeouts", and both mutating controls are DynamoDB ADD operations, so a retry would double-charge. The request id is claimed with a conditional write before the first mutation; a retry replays the stored verdict instead of re-applying it. A retry whose first attempt recorded no outcome fails closed, because there is no way to know whether it already charged.

Because the whole plane is fail closed, a (DEFAULT, BREAKGLASS) config row can bypass enforcement within the config cache TTL (~10s), no deployment. It is checked before the body is parsed, so it works even when the interceptor is rejecting malformed input. Every bypassed request is recorded with who set it and why.
Governance does not depend on the API shape. The gateway routes three inference contracts — /inference/v1/messages, /inference/v1/chat/completions and /inference/v1/responses — plus the runtime passthrough path, and each spells the prompt and the model differently: the model arrives in the body or in the URL, and the prompt lives in messages[], input/instructions, or a bare prompt.

A single _normalize() reduces whatever arrived to one internal contract — model, text units, tool specs, output ceiling — and every control reads that rather than the raw body. Text is harvested by structure, walking text-bearing keys recursively so tool results and nested content blocks yield their text, while opaque keys (bytes, source, s3Location) are skipped so image base64 is never scanned. Path matching is generic in the verb, so a new runtime operation still resolves its model, and a model that cannot be resolved fails closed.

Measured on the deployed stack: the same entitlement denial returns 403 through the Anthropic Messages shape, the OpenAI chat shape, the Responses shape, the runtime path, and all four runtime verbs — and a prompt injection hidden inside a Converse toolResult is caught. Every one produces an audit record naming the shape.

Clients & identity

Inference client

Jupyter walkthrough, or any base-URL + bearer client (curl, OpenAI SDK, Anthropic SDK). boto3 invoke_model is not the path — this is an LLM-provider REST API.

Admin browser

Governance console. Signs in with Cognito and must belong to gateway-admins.

Amazon Cognito — CDK-provisioned IdP

Browser-free USER_PASSWORD_AUTH, no client secret, so the notebook logs in with boto3 initiate_auth and no AWS credentials.

Group membership is the only identity axis. cognito:groups is already present in a standard access token, so the pool runs on FeaturePlan.LITE with no custom attributes and no pre-token-generation trigger. Everything else — models, rate, budget, guardrail — resolves from the config table at request time.

Authorizer configuration that matters. Cognito access tokens carry no aud claim — the client identity is in client_id. The gateway authorizer must therefore use allowed_clients only; setting allowed_audience demands a match that never succeeds. Inbound JWT validation is handled by AgentCore Identity and runs before interceptors, the policy engine and targets.

AgentCore Gateway — single endpoint, ordered enforcement
1

CUSTOM_JWT authorizer both surfaces

Validates issuer via the Cognito discovery URL and the app client via allowed_clients. Claims become Cedar principal tags.

2

REQUEST interceptor (Lambda) — runs first both surfaces

_normalize() first reduces whatever the caller sent — any path, any body shape — to one internal contract: model, text units, tool specs, output ceiling. Every control below reads that, never the raw body.

Model access · allow/deny globs from the config table → 403
Rate limit · fixed-window request + token counters per scope, optionally pooled across a group → 429
Cost budget · reserves worst-case output cost from the resolved output ceiling, charges the ledger → 429
Guardrail · calls ApplyGuardrail on the harvested text → 403, model never invoked
Writes a decision record and an audit record for every request.

Fail closed throughout. handler() is a thin wrapper that does nothing but call the governance body and convert anything it raises into a typed 403 — so a control added later cannot introduce a fail-open path by forgetting to handle something. A self-imposed deadline is checked before each control, and every dependency call carries an explicit connect/read timeout so one hung service cannot consume the budget (ApplyGuardrail gets a single attempt).

Retry-safe. The devguide warns that the gateway "may retry requests to interceptor Lambda functions in case of failures or timeouts", and both mutating controls are DynamoDB ADD operations — so a retry would double-charge. The request id is claimed with a conditional write before the first mutation; a retry replays the stored verdict instead of re-applying it.

One escape hatch. A (DEFAULT, BREAKGLASS) config row bypasses enforcement within the cache TTL (~10s), checked before the body is even parsed — because "the interceptor is rejecting everything" is exactly when you need it. Every bypassed request is recorded with who set it and why.

There is no native gateway rate limit in this stack. Both were removed, because a native limit attaches only on recognised inference paths (so the runtime passthrough is never metered), counts input tokens only (so it cannot bound generation), and keys on a scalar claim (so a shared team allowance is inexpressible). Verified: ListGatewayRateLimits returns 0. Rate limiting is the RATELIMIT config kind in layer 2 instead.

What serves as a backstop is not another native limit but two structural properties: layer 2 is fail closed, and layer 3 cannot time out. The reasoning, and why keeping a mantle-only limit was rejected, is in docs/FINDINGS.md.
3

Cedar policy engine both surfaces

Governs exactly one boolean: is the caller in the ai-platform group, i.e. may they use this gateway at all. Not which model, not how fast, not how much. Deny-by-default activates once any policy exists, so the set is an explicit permit plus a forbid — and the permit must leave the action unconstrained, because at runtime the action is the HTTP-suffixed child (bedrock___POST:/v1/messages) and a permit scoped to the parent matches nothing.

Its role in the design is to be the one check that involves none of our code and no Lambda that can time out. Everything expressive lives in layer 2; this layer exists so that a fault in layer 2 still cannot admit a caller who does not belong. Unlike the removed native rate limits, it applies on both surfaces.

Cedar cannot see the requested model — which is why entitlement lives in the interceptor and not here.

⚠️ The membership test is a substring match (like "*ai-platform*"), because cognito:groups is multi-valued and Cedar renders it as an opaque scalar. A group named former-ai-platform-users would also be admitted. Bounded here — passing the gate only reaches the interceptor — but tighten it before pointing this at a real directory.

4

RESPONSE interceptor (Lambda) — true-cost reconciliation buffers streaming

Normalizes usage across every naming convention the surfaces use (input_tokens, inputTokens, prompt_tokens, and the cache-token variants), prices it from the pricing table, replaces the reservation with actual spend, and enriches the decision record. It also harvests the response: assistant text digest, and which tools the model actually called (as opposed to which tools the caller merely offered). Attribution joins on REQUEST_ID from Lambda client context — the response payload contains no JWT at all. A 2xx it could not account for is emitted as unaccounted_success rather than silently dropped.

Five billable quantities, not two. Input, output, cache read, and cache write at the 5-minute and 1-hour TTL tiers — the 1-hour tier costs 1.6x the 5-minute one, so pricing cache writes as a single line item under-charges any request that used long caching. Where a provider reports only an aggregate (Converse does), it is attributed to the cheaper tier and the record is flagged cache_write_tier_assumed, so assumed spend stays distinguishable from measured spend.

Settle, never merely release. The rule across both interceptors: no output produced → refund; output produced but unmeasurable → keep the worst-case charge. So an unparseable success retains the reservation (a model did generate it), while a 4xx refunds — and this is the only layer that can refund a Cedar denial or an upstream error, because both happen after the REQUEST interceptor has already returned ALLOW. Either way the PENDING# row is deleted, so a surviving one always means "in flight" and never "settled".

Governance state (DynamoDB)

Governance config table

pk = scope: DEFAULT · GROUP#<g> · USER#<u>
sk = kind: MODELS · RATELIMIT · BUDGET · GUARDRAIL

Resolved USER → GROUP → DEFAULT, per kind. Entitlement is expressed as deny at DEFAULT, permit at GROUP# — allow-listing models for a group, with a per-user override where someone needs an exception. RATELIMIT and BUDGET are set at either level too.

Rules do not merge — only the first matching row for a kind is evaluated. So GROUP#ml-research re-grants opus by carrying its own rule with an empty deny list, not by subtracting from DEFAULT.

GUARDRAIL stores guardrail_version as well as guardrail_id. They are a pair: one id serves a mutable DRAFT and any number of published versions whose content policies can differ, so an id alone does not say what gets enforced.

Policy is runtime state: an admin edit is enforced within the ~10s interceptor cache TTL, no deployment.

⚠ Known gap — multi-group resolution is claim-order dependent. The scope chain walks a user's groups in the order the access token lists them and takes the first row it finds, with no priority field and no merge. Measured: alice is declared [ai-platform, ml-research] with precedence 1 and 2, and the token presents ['ml-research', 'ai-platform'] — reversed from the declaration and not ascending by precedence. So for a user whose groups both carry a row of the same kind, the winner is decided by an ordering nothing here sets or validates, and it is not "most restrictive wins".

Latent in this deployment because only one group carries a row of any given kind, and resolution skips scopes with no row for the kind being resolved. It is a documented future enhancement rather than a settled design — see docs/FINDINGS.md. Until it is addressed: one group per kind, with USER# rows for exceptions.

Cost ledger — four record kinds, one table

Spend counters per user per window · PENDING# reservations · RATE# rate-limit counters · DECISION#, one per request (user, groups, model, decision, status, tokens, true cost, 24h TTL).

Every kind expires via the ttl attribute, which is the name the table declares. A timestamp under any other name is just a number — the rate counters wrote expires_at for a while and were never reaped, invisibly, because the window bucket is part of the key so a stale row is never read again.

Plus SEEN#<request_id> idempotency markers. Anything that scans this table must skip the kinds it does not want — a reader that does not will report rate-limit counters as phantom zero-spend users.

Model pricing table

pk = normalized model_key; input, output and cache read/write prices. Refreshed daily from the AWS Price List API by a Lambda on an EventBridge schedule, and primed once on create.

Prices are runtime state for the same reason policy is: the hardcoded constants this replaced were 3x too high on opus-5. Both AWS service codes and both usagetype naming conventions are parsed, including the -mantle- usagetypes.

Admin console

API Gateway HTTP API → Lambda

Serves a single-file SPA and a JSON API. Authorization happens in code: the caller's access token is validated via GetUser, then gateway-admins membership is required.

Manages

Four screens: Model access · Rate & cost · Guardrails · Statistics. The first three write the config table the interceptor reads; the fourth reads the decision records.

Scope is always chosen from a picker over the real Cognito users and groups, never typed. A free-text GROUP#ml-reserch is accepted by the table and creates a rule that silently never matches — the console would then display policy that does not exist.

Because allow: ["*"] next to deny: ["*claude-opus*"] is not self-explanatory, the model-access screen also computes effective access: for a chosen user it shows the scope chain, which scope matched, and per model which glob decided the verdict. It evaluates request-shaped model ids, the same namespace the interceptor matches against — an earlier version used the pricing table's normalized keys and confidently reported the opposite of the truth.

The BREAKGLASS row is shown as a banner but is read-only here: turning governance off should be a deliberate CLI act, not a button.

Invariant, enforced at synth time. The public surface is API Gateway, never the Lambda itself. pilot/guards.py applies a CDK aspect that fails the build on any Lambda with a wildcard invoke principal or a Function URL with authType=NONE. "Authorize in code behind a public invoke endpoint" is not the same as "not publicly invokable", and the aspect exists so that distinction cannot be lost by accident. See docs/FINDINGS.md for the incident that prompted it.
▼   both hops: SigV4, signed with the ONE gateway execution role   ▼
What “passthrough” does and does not mean. It is the name of a gateway target type, not a statement about credentials. Both targets are configured credentialProviderType: GATEWAY_IAM_ROLE, so both upstream calls are SigV4-signed by the gateway execution role, and neither passes caller credentials through — the caller only ever holds a Cognito bearer token. The difference is how the SigV4 service name is chosen: an inference target derives it from the endpoint hostname, while a passthrough target is one of the few types allowed to state it explicitly. Runtime needs that override, which is the entire reason it is a passthrough target. What is passed through is the request body and path: passthrough does no schema translation, so the model id stays in the URL rather than being routed from the body.

bedrock-mantle inference target

Unified serverless surface — 110+ models across ~12 providers. Deployed twice for comparison: a zero-config connector and an explicit provider configuration (the default serving path).

Addressed at /inference/v1/messages. Model ids like anthropic.claude-sonnet-5.

Signing service is derived from the hostname — bedrock-mantle — which happens to be correct, so no override is needed.

bedrock-runtime HTTP passthrough

Classic runtime API incl. cross-region inference profiles. Cannot be an inference target: the gateway derives the SigV4 service from the endpoint hostname (bedrock-runtime) but runtime signs as bedrock, and the IamCredentialProvider override is rejected on inference targets.

Addressed at /bedrockrt/model/<modelId>/invoke — the inference router does not see passthrough targets. Model ids like us.anthropic.claude-sonnet-5.

Signing service is explicitly set to bedrock via IamCredentialProvider. Signing the identical request by hand with that service returns 200, which isolated the defect to the service name.

How one interceptor governs every request shape

The gateway is a single front door onto contracts that disagree with each other. Governance cannot depend on which one the caller used, so the interceptor never reads the raw body directly — it reads a normal form.

PathModel comes fromPrompt lives inOutput ceiling

_normalize(path, body) reduces all of that to one contract every control reads: {model, model_source, api_shape, surface, verb, streaming, text_units, max_output_tokens, tools}. Three properties matter:

Text is harvested by structure, not by field name. A recursive walk over text-bearing keys (text, content, toolResult, toolUse, input, arguments, json, parts, guardContent) collects prompt text wherever it sits — including inside tool results, which is the text an agent feeds back to itself and therefore attacker-controlled. Opaque keys (bytes, source, s3Location) terminate the walk, so image base64 is never scanned.

Path matching is generic in the verb. /model/([^/]+)/([A-Za-z0-9_-]+) rather than a fixed /invoke, so a runtime operation that does not exist yet still resolves its model and still gets governed.

An unresolvable model fails closed. If the target model cannot be determined from either the path or the body, the request is denied 403 model_unresolved — because entitlement and pricing are both unevaluable without it. The api_shape label also carries a trailing ? when it was inferred from the body rather than recognised from the path, so an unaccounted-for shape is one audit query away.
Why it is built this way rather than as a set of per-shape readers: three separate governance bypasses came from per-shape field lookups, one of which left Converse entirely ungoverned. The narrative, the measurements and the general lesson are in docs/FINDINGS.md.
The audit log — one place to answer "who asked what, and what did we do"

Why not Bedrock invocation logging

It is an account-level setting this stack does not own, mantle does not offer it, and it records the Bedrock call. A guardrail denial never reaches Bedrock, so the most security-relevant events would be missing entirely.

Why not the decision records

They carry a 24-hour TTL by design — they are operational state for the console, not an archive. The audit log is retained 90 days, and the Statistics tab links into it for anything older than its own window.

How it is wired

Both interceptors set the Lambda logGroup property to the same group. A structured print therefore lands in one destination — no PutLogEvents plumbing, no log-stream lifecycle, and no 5 TPS-per-stream throttling ceiling.

Content is hashed, not stored, by default. Prompt and response text are reduced to a SHA-256 plus a length — enough to correlate, to prove two calls were identical, and to detect tampering, without concentrating sensitive content in CloudWatch. AUDIT_LOG_PROMPT_TEXT and AUDIT_LOG_RESPONSE_TEXT turn the text on deliberately, with a character cap and a truncated flag.
A data protection policy is on regardless — 8 identifier types (email, credit card, SSN, US phone, AWS secret key, IP address, address, name) masked at ingest, with an Audit statement alongside the Deidentify statement so you can see what was found.

This is on even though content logging is off, because content is not the only leak path: guardrail assessments quote the offending span, error strings quote request fragments, and tool arguments carry whatever the caller put in them. A field you did not intend to be sensitive is exactly the field that leaks.

Reading the decision field

Decisions fall into four groups, and a dashboard that treats them alike is misleading — a policy denial is normal traffic, a fail-closed denial is an incident.

GroupDecisionsWhat it means
Allowedallowed · allowed_guardrail_off · allowed_no_prompt_textdispatched; the second two are configured outcomes, not failures
Denied by policymodel_access_denied · guardrail_blocked · rate_limit_exceeded · cost_budget_exceededexpected traffic meeting a rule
Fail closedgovernance_timeout · governance_unavailable · governance_retry_indeterminate · model_unresolved · unrecognised_shape · unparseable_bodyoperational signal — policy could not be established. Alarm on these.
Bypassedbreakglass_bypassgovernance is off right now, by administrator action
How a Cedar denial gets attributed: the REQUEST interceptor runs before Cedar, so its own record says allowed for a request Cedar then refuses. The RESPONSE interceptor resolves this, because it is the only component that sees both the interceptor's decision and the caller's actual status. It stamps final_status and final_layer onto the decision record and the audit record, keyed off a signal that needs no new field: a PENDING# row exists only on the allow path, so pending present + final ≥ 400 means a later layer refused, while no pending + final ≥ 400 means the interceptor itself did.

Two honest caveats. The gateway never reports a policy-engine decision to the response interceptor, so policy_engine is deduced from "we allowed it and the caller got a 403" — sound because Cedar is the only post-interceptor layer here returning 403. And a denial's RESPONSE record carries no username, since the response event has none; join on request_id.

Also relevant when querying: the RESPONSE interceptor does run after a REQUEST short-circuit, contrary to the documentation for HTTP targets, so an interceptor denial produces records at both stages.
Observability — one authoritative source, and two supporting ones

Interceptor decision records authoritative

Every request, with user identity, model, decision, the resolved final outcome and true cost. This is what the admin console reads and what every statistic is computed from.

Gateway OTEL spans → aws/spans diagnostics

Reveals the real qualifiedModelId, and which native layer answered. Deliberately not a governance statistic: interceptor short-circuits are not spanned at all, spans carry no identity or token counts, and of the two outcomes they distinguished, errorType=throttle is now impossible (both native rate limits were deleted) and errorType=user (Cedar) is resolved from the decision records instead. Available on request at /api/diagnostics/spans.

Central audit log retained

The same decisions as above, plus response-side tokens and true cost, in one CloudWatch group with 90-day retention and field indexes. This is the copy a security reviewer searches; the DynamoDB records are the copy the console reads.

Why they are kept separate: spans carry no identity and no token counts, and interceptor short-circuits are not spanned at all — measured, 10 interceptor decisions including 6 denials against spans showing a single 403. Blending them would silently undercount every governance denial.
The one configuration choice with a visible cost
Interception pointStreamingCan enforce
REQUEST onlypreservedmodel access, rate, guardrail, cost reservation
+ RESPONSEbufferedthe above, plus true output-token cost and response-side audit
A REQUEST interceptor completes before dispatch and never sits in the response path, so there is nothing to buffer. A RESPONSE interceptor runs in buffered mode only for HTTP and inference targets, and the buffering is not tunable — there is no chunk size or threshold, only the presence or absence of the interceptor.

Measured on this stack: request-only interception delivers a 5.4s spread of genuine progressive streaming (248 SSE events, first token 2.7s). With output-token accounting attached: same SSE format, same content, first token 7.4s and a 0.0s spread — every chunk arrives together.

This deployment enables output-token accounting, so streaming is buffered here. Set ENABLE_OUTPUT_TOKEN_ACCOUNTING = False in pilot/config.py to reverse the choice and fall back to prompt-only cost. Nothing else changes.
